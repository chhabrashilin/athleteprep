# GameIQ — Video Assets

> This document describes the video upload architecture, storage strategy, database model, permissions, playback strategy, and roadmap for video processing features.

---

## 1. Purpose

Video is the primary evidence source for GameIQ's AI analysis pipeline. In v1, the AI does not perform automated frame-by-frame video analysis — instead, coaches tag key moments manually as timestamps, and the AI uses those timestamps (plus coach notes and game metadata) to generate structured insights.

The video upload step is therefore:
1. A repository for the coach's reference film.
2. A future anchor for timestamp events (timestamps reference video time codes).
3. A foundation for future automated analysis (CV, player tracking, etc.).

## 2. Storage Architecture

### Bucket

| Bucket | Privacy | Max size per file | Env var |
|--------|---------|------------------|---------|
| `game-videos` | Private | 1 GB (documented) | `NEXT_PUBLIC_STORAGE_BUCKET` |

The bucket must be created manually in Supabase Dashboard → Storage. See `/docs/SUPABASE_SETUP.md` for instructions.

### Storage Path Format

Videos are stored in a team- and game-scoped path:

```
teams/{teamId}/games/{gameId}/videos/{timestamp}-{sanitized-filename}
```

Example:
```
teams/a1b2c3d4/games/e5f6g7h8/videos/1717200000000-match-vs-usc.mp4
```

- The millisecond timestamp prefix guarantees uniqueness and prevents accidental overwrites.
- The filename is sanitized to remove unsafe characters.
- This path structure provides implicit team isolation even if storage policies are broad.

### Path Building (`lib/storage/videos.ts`)

```ts
buildGameVideoStoragePath(teamId, gameId, fileName)
sanitizeFileName(fileName)
```

### Playback URL Strategy

The bucket is **private** — no anonymous access. Video playback uses **signed URLs**:

- Generated server-side using the authenticated Supabase server client.
- Signed URL expiry: **1 hour** (`SIGNED_URL_EXPIRY_SECONDS = 3600`).
- After expiry, the user must refresh the page to get a new signed URL.
- Generated by `createSignedVideoUrl(videoAsset)` in `lib/db/video-assets.ts`.

This ensures:
- Private videos are never exposed via public URLs.
- Each access requires the user to be authenticated.
- URL sharing is limited to the expiry window.

## 3. Database Model

Stored in the `video_assets` table (defined in `supabase/migrations/0001_initial_schema.sql`).

| Column | Type | Notes |
|--------|------|-------|
| `id` | uuid | PK |
| `team_id` | uuid | FK → teams |
| `game_id` | uuid | FK → games |
| `uploaded_by` | uuid | FK → profiles |
| `storage_bucket` | text | e.g. "game-videos" |
| `storage_path` | text | Full path within bucket |
| `public_url` | text | null in v1 (reserved for CDN) |
| `file_name` | text | Sanitized filename |
| `file_size_bytes` | bigint | Client-reported size |
| `mime_type` | text | Client-reported MIME type |
| `duration_seconds` | numeric | Extracted client-side via HTML5 video |
| `thumbnail_path` | text | null in v1 (future FFmpeg) |
| `upload_status` | enum | pending / uploading / uploaded / failed |
| `processing_status` | enum | not_started / pending / processing / completed / failed |
| `processing_error` | text | Error message if upload_status = 'failed' |
| `metadata` | jsonb | Reserved for future codec/resolution data |

All new records are created with `upload_status = 'uploaded'` and `processing_status = 'not_started'`.

## 4. Upload Flow

### Client-side upload (no server buffering)

Large video files are uploaded **directly from the browser to Supabase Storage**, bypassing the Next.js server. This prevents memory exhaustion on the server for files up to 1 GB.

Flow:

```
1. User selects file via drag-and-drop or file picker (VideoUploadCard)
2. Client validates: MIME type, extension, file size
3. Client extracts video duration via HTML5 video element (best-effort)
4. Client calls supabase.storage.from(bucket).upload(path, file)
   → Uses browser Supabase client (getSupabaseBrowserClient())
5. On storage upload success:
   → Client calls saveVideoAssetAction(input) [server action]
   → Server creates video_assets DB row
   → Server returns created VideoAsset
6. On server action success:
   → Client calls router.refresh() (re-fetches server-rendered page with video player)
7. On any failure:
   → If storage upload succeeded but DB insert failed:
     → saveVideoAssetAction attempts tryDeleteStorageObject() (best-effort cleanup)
   → Error is displayed to user
```

### Key files

| File | Role |
|------|------|
| `lib/storage/videos.ts` | Path building, sanitization, validation, duration extraction |
| `lib/constants/video.ts` | Allowed types, max size, bucket name |
| `lib/actions/video.ts` | `saveVideoAssetAction`, `deleteVideoAssetAction` |
| `lib/db/video-assets.ts` | DB queries + signed URL generation |
| `components/video/VideoUploadCard.tsx` | Upload UI (drag-drop, progress, success, error) |

## 5. File Validation

Validated **client-side** in `VideoUploadCard` before upload starts:

| Rule | Value |
|------|-------|
| Allowed MIME types | video/mp4, video/quicktime, video/webm, video/x-msvideo |
| Allowed extensions | .mp4, .mov, .webm, .avi |
| Max file size | 1 GB (1,073,741,824 bytes) |

The server action (`saveVideoAssetAction`) does not re-validate file content — it trusts the storage upload success as implicit validation. The storage bucket policies prevent non-video MIME types from being accepted if configured correctly.

## 6. Permissions

| Action | owner | coach | analyst | player | viewer |
|--------|-------|-------|---------|--------|--------|
| View video (signed URL) | ✅ | ✅ | ✅ | ✅ | ✅ |
| Upload video | ✅ | ✅ | ✅ | ❌ | ❌ |
| Delete video | ✅ | ✅ | ✅ | ❌ | ❌ |

Authorization is enforced at two layers:
1. **Application layer**: `VideoUploadCard` receives `canEdit: boolean` from server; non-staff see a "coaches and analysts only" message.
2. **RLS layer**: `video_assets` INSERT requires `is_team_staff`. DELETE requires `is_team_manager` (owner/coach). Storage policies require authentication.

## 7. Storage Policies

The `game-videos` bucket requires storage policies applied in Supabase. See `supabase/migrations/0003_storage_policies.sql` for the SQL.

Because storage policies live in the `storage` schema (not `public`), they may need to be applied via the Supabase Dashboard → Storage → Policies rather than via `supabase db push`.

Summary:
- `INSERT`: authenticated users only
- `SELECT`: authenticated users only (required for signed URL generation)
- `UPDATE`: authenticated users only
- `DELETE`: authenticated users only

Application-layer team scoping (storage path + video_assets RLS) prevents cross-team access even with these broad policies.

## 9. Current Limitations

- **No progress percentage**: The Supabase storage upload shows a spinner but no exact progress bar. This is acceptable for v1.
- **No multi-video selection**: Each game can have multiple video_assets rows, but the UI shows only the primary (most recent) video. Additional videos are stored but not displayed yet.
- **No server-side duration extraction**: Duration is extracted client-side via HTML5 video element. If the browser can't read metadata (e.g. certain AVI files), duration is stored as null.
- **No thumbnail generation**: `thumbnail_path` is always null. FFmpeg-based thumbnail extraction is a future enhancement.
- **1-hour signed URL expiry**: After an hour, the playback URL expires and the user must refresh the page. This can be extended via `SIGNED_URL_EXPIRY_SECONDS`.
- **Storage policy must be applied manually**: The policies in `0003_storage_policies.sql` may need to be applied via the Supabase Dashboard rather than CLI.
- **No upload chunk/resumable**: Large files (>500 MB) may fail on slow connections. Supabase Storage's TUS resumable upload protocol is a future integration.

## 10. Future Roadmap

### Phase 8 — Timestamp Integration
- Timestamps will reference `video_asset_id` for video-linked evidence
- `GameVideoPlayer` will support `initialTimestampSeconds` prop for jump-to-timestamp
- `onTimeUpdate` callback will feed the timestamp editor

### Server-side Video Processing (Phase 9+)
- FFmpeg job to extract: actual duration, resolution, frame rate, codec
- Thumbnail generation at regular intervals (stored in `game-thumbnails` bucket)
- `processing_status` transitions: `not_started` → `pending` → `processing` → `completed`
- Realtime status updates via Supabase Realtime subscription

### Resumable Upload (Phase 9+)
- TUS protocol support via Supabase Storage for reliable large file uploads
- Chunked upload with progress percentage

### Automated Video Analysis (Future)
- Computer vision microservice (separate from Next.js)
- Ball and player tracking
- Automated event detection
- Heatmaps and zone analysis

### Clip Extraction (Future)
- `clips` table stores `start_seconds`, `end_seconds` references to `video_assets`
- FFmpeg job extracts physical clip files on demand
- Clips linked to coaching insights for direct evidence playback
